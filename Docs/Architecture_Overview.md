# DX12Framework アーキテクチャ解説

このエンジンが **Engine / Editor / Game / Renderer** の4つでどう分かれていて、
1フレームの中で何がどの順に起きるのかをまとめた資料です。

読む順番としては

1. 全体像（4つの層）
2. 1フレームの流れ
3. 描画の流れ（Renderer）
4. データの流れ（GameObject と Component）
5. エディタの流れ（Editor）
6. 依存の向きと、迷ったときの判断基準

としています。

---

## 1. 全体像 — 4つの層

```
┌──────────────────────────────────────────────────────────┐
│ Application            ウィンドウ / メインループ / 入力の変換  │
│                        プラットフォーム(Win32)を知る唯一の層   │
└───────────────┬──────────────────────────────────────────┘
                │ 所有
    ┌───────────┼───────────────┬──────────────┐
    ▼           ▼               ▼              ▼
┌────────┐ ┌──────────┐ ┌──────────────┐ ┌──────────┐
│ Engine │ │ Renderer │ │ SceneManager │ │  Editor  │
│  基盤   │ │  描き方   │ │  シーンの管理 │ │  編集画面 │
└────────┘ └──────────┘ └──────┬───────┘ └──────────┘
                                │ 所有
                                ▼
                           ┌────────┐
                           │  Game  │  ゲーム固有の中身
                           │GameScene│ （このプロジェクトの遊びの部分）
                           └────────┘
```

| 層 | フォルダ | 担当 | 担当しないこと |
|---|---|---|---|
| **Application** | `Source/Application` | ウィンドウ、メインループ、Win32の入力とカーソル | 何を描くか、何を編集するか |
| **Engine** | `Source/Engine` | オブジェクト・コンポーネント・アセット・入力・カメラなど、ゲームにもエディタにも共通する土台 | 具体的なゲームの中身 |
| **Renderer** | `Source/Engine/Renderer`, `Source/Engine/RHI` | DX12そのものと、描画手順 | 何を描くか（それはシーンが決める） |
| **Editor** | `Source/Editor` | ヒエラルキー・インスペクタ・履歴など、編集のための画面と操作 | オブジェクトの実体の持ち方 |
| **Game** | `Source/Game` | このプロジェクト固有のシーン | 描画APIの詳細 |

### 「Engine と Editor のどちらに置くか」の基準

このプロジェクトで何度か迷った点なので、判断基準を明文化しておきます。

> **エディタが無い状態（ゲームとして起動したとき）でも必要か？**
> 必要なら Engine、編集画面にしか関係しないなら Editor。

この基準で、次のものは Engine 側へ置いています。

| もの | 理由 |
|---|---|
| `GameObjectFactory` | オブジェクトを作る・複製するのは、実行中のゲームでも必要 |
| `ComponentRegistry` | ファイルから復元するには型名で扱う仕組みが要る |
| `PrefabAsset` / `SceneAsset` | 完成したゲームもシーンを読み込んで起動する |
| `ModelLibrary` | モデルの読み込みと所有は編集とは無関係 |

一方、次のものは Editor 側です。

| もの | 理由 |
|---|---|
| `ComponentInspectors` | 「Transform という日本語表示名」「削除ボタンを出すか」は編集画面の都合 |
| `ObjectCommands` / `CommandHistory` | Undo は編集のための仕組み |
| `PrefabSystem` / `SceneEditor` | 「コンテンツブラウザで開いているフォルダへ保存する」は編集画面の都合 |

## 2. 1フレームの流れ

`Application::Tick()` が1フレームの全体です。順番には理由があります。

```
 1. ApplyPendingResize()        ウィンドウサイズの変更を反映
        │                        描画にもUIにも関わるため最初に済ませる
        ▼
 2. InputManager::Update()      キーとマウスの状態を確定
        │
        ▼
 3. UpdateEditorUI()            ★ エディタUIの組み立て
        │  ├ Context::NewFrame()      入力を配り、ホバー/フォーカスを決める
        │  ├ EditorApp::BuildUI()     メニュー・パネル・ウィジェットを積む
        │  └ Context::EndFrame()      Z順に並べて描画データを確定
        │
        │  ここでシーンが書き換わる（オブジェクトの作成・削除など）
        ▼
 4. マウスの持ち主を決める        UIが掴んでいなければカメラへ渡す
        │
        ▼
 5. SceneManager::Update()      ★ シーンの更新
        │  └ GameScene::OnUpdate()
        │       ├ SyncRenderComponents()  描画コンポーネントに実体を結び付ける
        │       ├ ObjectManager::Update() 各Componentの更新
        │       └ FlushPendingRemoves()   削除予約の実行
        ▼
 6. BeginFrame()                コマンドリストの記録開始
        │
        ├ EditorApp::RenderPanels()      自前の描画先を持つパネル（エフェクト等）
        ├ RenderSceneToViewport()        ゲーム画面をパネル用テクスチャへ
        ├ EditorUIRenderer::Render()     UIをバックバッファへ
        ▼
 7. EndFrame() → Present()
        ▼
 8. SceneManager::ProcessSceneChange()   シーン切り替えの実行（遅延）
```

### 順番で特に重要なところ

**UIの組み立て(3)がシーンの更新(5)より前**
UI操作でオブジェクトを増減させても、その結果がそのフレームの更新と描画へ反映されます。
また、`Update` / `Submit` のループの外なので、オブジェクトの一覧を安全に作り直せます。
シーンの読み込みが「UIの組み立て中」に行われるのはこのためです。

**削除がフレーム末(5の最後)**
`Remove()` は予約だけを行い、実際に消えるのは `FlushPendingRemoves()` です。
ループの途中で一覧が変わらないようにするためです。

**シーン切り替えが一番最後(8)**
描画コマンドを積んだあとに切り替えることで、
GPUがまだ使っているリソースを壊さずに済みます。

## 3. 描画の流れ（Renderer）

描画は下から順に4段になっています。

```
┌─────────────────────────────────────────────────────┐
│ GameScene           何を描くか（オブジェクトとカメラ）  │
└──────────────┬──────────────────────────────────────┘
               ▼
┌─────────────────────────────────────────────────────┐
│ SceneRenderer       どういう手順で描くか               │
│   MainPass → PostProcess → 出力先へ                  │
└──────────────┬──────────────────────────────────────┘
               ▼
┌─────────────────────────────────────────────────────┐
│ RenderGraph / RenderQueue   パスの依存とバリア、描画順  │
└──────────────┬──────────────────────────────────────┘
               ▼
┌─────────────────────────────────────────────────────┐
│ RHI (Device / CommandList / Buffer / PSO ...)        │
│   DX12のAPIを直接触る唯一の層                          │
└─────────────────────────────────────────────────────┘
```

### 描画データの集まり方

```
GameObject
   └ MeshComponent::Submit(RenderQueue*)
         │  ワールド行列を定数バッファへ書き、DrawItemを1つ積む
         │  ここではDX12のAPIを一切呼ばない（並列化できるようにするため）
         ▼
     RenderQueue   DrawItemをためる
         │
         ▼
     RenderQueue::Execute(cmdList)   ためた分をまとめてコマンドリストへ
```

**Submit と Execute を分けている理由**
`Submit` は「描きたいものを申告する」だけで、DX12を触りません。
そのため将来オブジェクトの更新を並列化しても、そのまま使えます。
実際にコマンドを記録する `Execute` だけが単一スレッドで動きます。

### 出力先（SceneOutput）

ゲーム画面はバックバッファ固定ではありません。
エディタのビューポートパネルへ描くため、毎フレーム出力先が差し替わります。

```
ViewportPanel が必要な大きさを申告
   → Application が ViewportTarget を作り直す
   → SceneManager::SetSceneOutput() でシーンへ伝える
   → GameScene がカメラの縦横比も合わせる
   → SceneRenderer が以降そのSceneOutputだけを見る
```

### 2つの描画経路

| 経路 | コンポーネント | 特徴 |
|---|---|---|
| 通常 | `MeshComponent` | 頂点シェーダー + ピクセルシェーダー |
| メッシュシェーダー | `MeshletComponent` | モデルをメッシュレットへ分割して描く |

同じモデルを両方で描いて比べられるようにしてあります。

## 4. データの流れ（GameObject と Component）

### コンポーネント指向

```
GameObject （基底クラスのみ。派生させない）
   ├ TransformComponent   位置・回転・大きさ
   ├ MeshComponent        通常描画
   └ MeshletComponent     メッシュシェーダー描画
```

「プレイヤー」「敵」といった派生クラスは作りません。
必要な機能はコンポーネントを足して表します。
そのため**エディタから機能を付け外しできる**ようになっています。

### 「希望」と「実体」を分ける

このエンジンで一番の要になっている考え方です。

```
MeshComponent が持つのは
   ・どのモデルの、何番目を描きたいか   ← 希望（ただの文字列と数値）
   ・いま実際に結び付いている Mesh*     ← 実体

  この2つがずれていたら、シーンが毎フレーム直しに来る
        GameScene::SyncRenderComponents()
```

**なぜ分けるのか**

コンポーネントが自分でモデルを読み込もうとすると、
デバイスもモデルの置き場も知らなければならず、
「ただのデータ」ではなくなってしまいます。
すると保存も復元もできません。

希望だけを持たせておくと

* コンポーネントは保存・復元できる値のままでいられる
* エディタから割り当てても、ファイルから読み込んでも、同じ道を通る
* モデルがまだ読み込まれていなくても、あとから解決される

という3つが同時に成り立ちます。

```
エディタでモデルを選ぶ ─┐
プレファブから復元    ─┼→ SetModelRequest（希望を書くだけ）
シーンから復元        ─┘          │
                                  ▼
                    次のフレーム、GameScene が
                    ModelLibrary から実体を引いて結び付ける
```

### 保存と復元は1本の道

複製・プレファブ・シーン・「コンポーネント削除の取り消し」は、
どれも「今の値を写して、あとで戻す」という同じ処理です。
そこで経路をJSON1本にまとめています。

```
        ComponentRegistry
            Save(GameObject → json)
            Load(json → GameObject)
                    │
      ┌─────────────┼─────────────┬────────────────┐
      ▼             ▼             ▼                ▼
   複製          プレファブ      シーン        コンポーネント
                                              削除の取り消し
```

新しいコンポーネントを足すときに `ComponentRegistry.cpp` の表へ1項目書けば、
この4つが同時に対応します。

## 5. エディタの流れ（Editor）

### パネルは互いを知らない

```
        EditorContext（参照の束）
   ┌────────┬────────┬─────────┬────────┐
   ▼        ▼        ▼         ▼        ▼
Hierarchy Inspector Content  Viewport  Effect
                     Browser           Editor
```

パネル同士は直接参照しません。
共有したいものは `EditorContext` に置き、
「選択」は `Selection`、「パネルの開閉」は `PanelManager` を介します。
そのため、パネルは1枚ずつ独立して足したり消したりできます。

### シーンを書き換えるときは必ず履歴を通る

```
メニューバー ─┐
ヒエラルキー ─┼→ ObjectCommands ─→ CommandHistory ─→ GameObjectFactory
インスペクタ ─┘   ComponentCommands   （履歴）        （生成・出し入れ）
```

パネルから直接オブジェクトを書き換える道を用意していないため、
**取り消せない操作が混ざることが構造的に起きません。**

### 削除は「壊さない」

```
削除      : シーンから外す → 実体はコマンドが預かる
元に戻す  : 預かっていたものをそのまま戻す
```

破棄して作り直す方式だと、IDもポインタも変わり、
コンポーネントの初期化状態も失われます。
`GameObjectManager::Detach()` で実体を生かしたまま外すことで、
「完全に元通り」を実現しています。

## 6. 依存の向きと、迷ったときの判断基準

### 依存は必ず下向き

```
Application  →  Editor  →  Engine  →  RHI
     │             │
     └──→ Game ────┘
```

* **Engine は Editor を知らない** — エディタが無くても動く
* **EditorUI は Windows を知らない** — キーもカーソルも `Application` が翻訳する
* **RHI より上は DX12 の型をなるべく持たない**

逆向きの依存が必要になったときは、
「値だけを渡して、実際の処理は上の層にやってもらう」形へ直します。
たとえばマウスカーソルは、EditorUI が
「Iビームにしたい」という希望を立てるだけで、
実際に `SetCursor` を呼ぶのは `Application` です。

### 新しい機能をどこへ置くか

```
その機能は…

  DX12のAPIを直接触る？          → Engine/RHI
  描き方の手順？                  → Engine/Renderer
  オブジェクトやアセットの扱い？    → Engine
  編集画面での見せ方・操作？        → Editor
  このゲーム固有の遊び？            → Game
  ウィンドウやOSの都合？            → Application
```

迷ったら「エディタが無くても必要か」を先に考えると、
Engine と Editor の境目はほぼ迷わなくなります。
